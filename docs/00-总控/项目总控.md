# 个人工作台项目总控

> 状态：执行基线
>
> 维护日期：2026-08-03

## 1. 项目目标

提供三个可独立使用的个人工作台：

| 入口 | 主要用户 | 当前定位 |
| --- | --- | --- |
| 成人成长工作台 | 成人本人 | 自律、学习、阅读、目标和生活分区 |
| 儿童学习工作台 | 小学阶段 | 学习任务、错题、阅读、成长和奖励 |
| 幼儿学习工作台 | 幼儿园大班到小学低年级过渡 | 少文字、大图卡、短活动、花园反馈 |

项目当前的主线不是同时把三套产品做成完整教育平台，而是保持三个入口稳定，集中验证幼儿版的“今日打卡 → 简单测试 → 阳光/奖励 → 进入游戏”闭环。

工作台和游戏明确分层：工作台是安静、快速的控制台；游戏是趣味、动画和沉浸互动发生的地方。工作台不承担完整教材引擎，课程资料库也不等于必须全部接入运行时。

## 2. 当前主目标

当前唯一主目标：

> 在不破坏成人版、儿童版和现有本地快照的前提下，让幼儿版形成一个可以连续使用 14 天的本地优先打卡闭环。

### 14 天闭环必须包含

- 首页只突出今日 3 项核心打卡，可选项目默认折叠。
- 每项打卡只需要一个清晰的完成动作或简单测试，不要求打开完整课程系统。
- 完成打卡只通过统一奖励事件发一次阳光；豌豆能量与阳光分开。
- 工作台提供“去游戏”出口，游戏内再承载动画、植物选择、战场互动和趣味反馈。
- 花园、植物、僵尸只反馈打卡状态，不惩罚、不扣学习资源。
- 刷新、导入导出、离线打开后，进度和奖励口径保持一致。

## 3. 明确不纳入当前主目标

- 不在当前阶段实现完整的植物大战僵尸塔防、复杂敌人 AI 或多关卡战斗。
- 不把工作台扩展成 60 日 × 全学科完整课程引擎；60 日资料可以保留在资料库，按需逐科接入。
- 不把趣味动画、角色和游戏战斗塞进工作台首页。
- 不把 Supabase 重新作为运行时后端；当前自托管 API 只保留适配边界。
- 不同时重构成人版、儿童版和幼儿版的大文件。
- 不把未经授权的商业教材、原版角色、截图和网络图片放进发布制品。
- 不把 APK 编译成功当作产品完成；网页闭环和安装后核心流程都要先通过验收。

## 4. 技术边界

| 层 | 当前事实 | 约束 |
| --- | --- | --- |
| 页面 | Vanilla JS 静态 SPA，三个独立入口 | 不维护第二套 Android 页面 |
| 状态 | 各入口独立 localStorage 快照 | 不新增第二套积分账本；新 key 必须登记 |
| 内容 | 静态 JSON/JS 数据与资料库 | 先 schema 和内容 QA；资料库不自动等于运行时课程 |
| 奖励 | 阳光、累计成长、豌豆能量分离 | 通过唯一事件 ID 防重复结算 |
| 同步 | 自托管 API 适配层预留 | 离线优先，不能把网络成功写成默认事实 |
| 发布 | GitHub Pages + Capacitor Android | Pages 制品和 APK 使用同一份运行资源 |

## 5. 完成定义

### 功能完成

- 页面入口可达。
- 主操作能完成或明确失败。
- 数据刷新后仍存在。
- 重复点击、重复进入和重复导入不会重复发奖。
- 对应测试或手工验收证据已记录。

### 课程完成

- 有目标、活动步骤、成功证据和复习安排。
- 内容字段通过 schema/QA。
- 有原创或明确授权的资料来源。
- 能进入今日活动，而不是只停留在展示卡片。

### 工作台完成

- 今日任务少而明确，孩子可以快速完成和查看结果。
- 打卡、简单测试、奖励和备份闭环可验证。
- 复杂趣味内容通过独立游戏入口访问，不挤占工作台主流程。

### 游戏完成

- 游戏可以独立进入、操作、结束并反馈结果。
- 游戏趣味不影响打卡正确性，也不直接决定课程掌握度。
- 游戏失败可以重来，不扣除孩子已有阳光或学习进度。

### 发布完成

- `npm test` 全部通过。
- Pages 制品组装和深层入口检查通过。
- APK Actions 成功并下载到本地。
- MuMu 安装后完成启动、课程、花园、奖励和离线流程。

## 6. 变更前的五个问题

1. 这是当前主目标的一部分，还是新想法？
2. 会不会引入新的状态、奖励、日期或路由边界？
3. 现有模块和数据是否已经能复用？
4. 完成后用哪个测试、截图或文件证明？
5. 如果本次不做，是否应记录为冻结项，而不是继续堆在进行中？
