# 全项目学习游戏优化调研

日期：2026-08-24

## 一句话判断

工作台已经“有内容、有画面、有语音、有游戏”，下一阶段应从功能集合升级为学习系统：每次作答产生可信证据，复习和新内容按节奏编排，游戏消费真实掌握度，所有结果回到同一成长档案。

完整联网证据位于：`output/research/20260824-learning-game-optimization/`。

## 当前优势

- 识字 1,500 字、英语 597 词及拼音、古诗、数学、拼读已经形成离线内容底座。
- 识字与英语已有尝试次数、错题、复习日期和掌握状态，说明统一闭环不需要重写整个项目。
- 三个主题世界、专注小游戏、成长宠物和阳光奖励已经具备游戏外循环。
- Capacitor Android、离线音频与本地存储符合儿童场景的断网使用要求。
- 识字页面当前视觉层级、卡片美术和语音入口已经达到可继续精修的基础。

## 核心缺口

### 1. 掌握度被高估

`prj/app.js` 的 `recordSubjectProgressFromLesson()` 在课程结束时调用 `markSubjectReady()`，把拼音、古诗、数学、拼读整轮内容直接置为 `ready`。这绕过了各科 `review-rules.json` 中的 1/3/7/14 天间隔、两个日期、两种活动和 80% 准确率要求。

后果是课程进度、解锁等级和游戏难度都可能领先于真实能力。

### 2. 游戏与学习仍是两条线

部分玩法仍是“先答题，再播放攻击/庆祝”，学习动作本身没有改变路线、落点、资源或敌人状态。`G:\StudyCode\小游戏项目\pinyin-star-scout` 的“选路线就是拼音判断”更接近目标，应作为首个机制级接入样板。

### 3. 奖励与难度存在状态风险

- `countLiteracyKnown()` 当前统计掌握表全部 key，练习中的字也会提高难度。
- `recordPlaySession()` 持有旧状态时调用会独立读写存储的奖励函数，最后再写回旧状态，存在覆盖刚发阳光的风险。

### 4. 横屏显示浪费主要空间

800×360 实测中，侧栏约 175px，主区却从 x≈423px 才开始，内容只剩约 362px。原因是末层样式把固定侧栏改成 flex 子项，而主区仍保留 248px 左边距，偏移被重复计算。

## 目标结构

```text
今日编排器
  ├─ 到期复习 1–2 个
  ├─ 新内容 2–4 个
  └─ 迁移挑战 1 个
          ↓
统一作答事件 attempt
  ├─ 科目 / 内容 key / 活动类型
  ├─ 正误 / 日期 / 是否提示
  └─ 错误标签
          ↓
掌握引擎
  introduced → practicing → ready → maintenance
          ↓
课程解锁、小游戏难度、成长报告、阳光奖励
```

## 分阶段裁决

### P0：可信学习闭环和可用横屏

- 拼音、古诗、数学、自然拼读逐题写入尝试、正确数、日期、活动类型、准确率和下次复习。
- 取消“整节完成即全量 ready”。
- 识字游戏难度只统计 `ready/maintenance`。
- 奖励与游玩状态在同一状态对象内原子更新。
- 修复 800×360 普通 Web 横屏双重侧栏偏移，并核验 Android 横屏。

### P1：首个机制级游戏接入

- 以 `pinyin-star-scout` 为样板接入统一桥协议。
- 每局 3–5 分钟，路线选择直接是拼音判断。
- 错误标签、提示使用和独立答对全部回写长期档案。
- 加入练习模式、速度档位、暂停和减少动态效果。

### P2：活动插件与课程编排

- 参考 Sugarizer/Antura，把活动从 `app.js` 中逐步拆成注册式模块。
- 统一 `attempt/result/session-summary` 数据合同。
- 课程编排器按“到期复习优先、少量新内容、活动交错、掌握后解锁”生成每日路线。
- 家长报告展示真实证据，而不是只展示完成次数。

## 不做的事

- 当前阶段不继续批量生成装饰图片；先解决学习闭环和显示契约。
- 不直接复制 GPL 项目代码。
- 不直接移植 Unity/Qt/Cocos2d-x 工程。
- 不把第三方课程内容或资产打入 APK，除非许可证和署名已逐项确认。
