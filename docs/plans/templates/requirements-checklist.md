# Txxx — 需求分解打勾确认表

> 这是整条链路的短控制面。需求讨论后先生成，后续方案审查、计划审查、代码审查、测试审查、最终验收都对照它。
>
> 在进入方案冻结前，先对照 `source-requirements-alignment.md` 确认：原始需求文档里的点，已经逐条映射到这张表，避免“后续审查都很认真，但审查的是错误基线”。

## 使用说明

- `人工确认`：需求讨论后先打勾 / 修订
- `方案审查`：确认方案有没有覆盖该需求点
- `计划审查`：确认 steps / acceptance / test-plan 有没有落到该需求点
- `代码审查`：确认实现有没有真的落地
- `测试审查`：确认验证有没有覆盖
- `最终验收`：确认该点最终闭合

先做一件事：

- 先把原始需求文档列进 `source-requirements-alignment.md`
- 逐条确认原始需求点是否已经映射到本表
- 如果原始需求里有内容还没进入本表，不要急着进方案和计划，先补齐

回写原则：

- 不要默认由实现者自己一路打勾到底
- `方案审查`、`计划审查`、`代码审查`、`测试审查` 优先由独立审查者回写
- 推荐优先使用 `review-with-subagent` 产出独立审查结论，再据此更新本表
- 如果确实由主代理暂代回写，备注里要说明依据的审查工件路径
- 如果审查中发现“原始需求文档里有点没进表”，先回补 `source-requirements-alignment.md` 和本表，再继续后续阶段

状态建议：

- `待确认`
- `OK`
- `缺失`
- `待补证据`
- `不适用`

## 约束变更类型标注

> 防止"需求变了"和"执行跑偏了"被混为一谈。两类变更的后续动作不同。
> 来源：Agent-CoEvo 约束共演化思路 + T008 教训。

当执行/测试/审查中发现原需求需要调整时，标注变更类型：

| 变更类型 | 含义 | 后续动作 |
|---------|------|---------|
| `clarified` | 原需求模糊，现在明确了 | 更新文档，继续执行 |
| `expanded` | 范围扩大，超出原始需求 | 需要重新 gate 确认 |
| `corrected` | 原需求有误，需要纠正 | 必须用户确认 |
| `implementation_drift` | 执行跑偏，非需求变化 | 回退到方案审查 |

在需求表中用备注列标注，例如：`R3 变更：expanded — 新增 p98 门禁（T008 教训）`

## 测试映射约定

- `计划测试阶段`：先写这个需求点预计在哪个阶段被验证
  - 例如：`阶段 2：最小主链路`
  - 或：`阶段 3：关键边界 + 阶段 4：阶段回归`
- `验证命令`：验证这个需求点的具体命令
  - 例如：`pytest tests/test_auth.py -k test_login`
- `预计时长`：验证命令跑完的大致时间
  - 例如：`≤30 秒`、`≤5 分钟`
- `测试证据`：测试完成后回写对应证据路径
  - 例如：`test-report.md#阶段-2`、`output/run-001/result.json`

> 在需求分解阶段就把验证命令和时长填进去，而不是等到 test-plan 才想。
> 这直接来自”粒度三问”的第一问：验证能在 10 分钟内跑完吗？

这样后面审查时，不只是问”有没有测试”，而是能直接追到”R3 到底在哪一轮被验证过”。
