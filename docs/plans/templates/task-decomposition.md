## 3. 任务类型判断

> 不同类型的任务有不同的默认粒度上限。

| 类型 | 判断 | 粒度上限建议 |
|------|------|------------|
| 只读分析（梳理、输出报告，不改代码） | 是 / 否 | 无限制，但输出必须可复查 |
| 隔离修改（单文件/单组件，无跨层依赖） | 是 / 否 | ≤3 个文件，≤100 行 diff |
| 跨层修改（前后端 / 数据库 / 中间件同时改） | 是 / 否 | 必须拆分，每层独立子任务 |
| 有隐性业务规则的修改 | 是 / 否 | 必须先做只读分析子任务 |

## 8. 分解后冒烟验证

> 分解表写完后，不要直接进入实现。先跑一遍最小验证，确认这份分解不是纸面成立、落地就炸。

- [ ] 分解项 ID 唯一，没有重复或跳号混乱
- [ ] 若已填写 `落地任务 ID`，能够被 `taskctl` 扫描到
- [ ] 每条 `验证命令` 的关键脚本 / 测试文件真实存在
- [ ] `上游依赖` 引用的分解项确实存在，不引用空气节点
- [ ] 若已落地为真实任务，`depends_on` 与 `allowed_paths` 不违背本表约束

```bash
# 1) 查看当前任务可见性（若已经创建真实任务）
python .claude/scripts/taskctl.py list-task-meta

# 2) 对当前分解表做冒烟验证
python .claude/scripts/taskctl.py verify-decomposition \
  --file docs/plan/tasks/{任务目录}/task-decomposition.md

# 3) 若这批子任务已经具备真实验证命令，再执行真实冒烟
python .claude/scripts/taskctl.py verify-decomposition \
  --file docs/plan/tasks/{任务目录}/task-decomposition.md \
  --run
```

> 若这一步失败，先修 `task-decomposition.md` 或子任务 `.meta.yaml`，不要带着已知断链进入 `steps.md`。
> `--run` 适合已经写好真实 pytest / python / cmd 验证命令的任务；若还是模板占位 `{command}`，先补成真实命令再跑。
