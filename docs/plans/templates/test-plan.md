> 定义“怎么验证任务通过”，以及是否需要日志采集与日志分析。

## 测试目标

- [ ] 验证主路径
- [ ] 验证关键边界
- [ ] 验证回归风险

> 来源提示：
> - 主路径优先来自 `核心目标`
> - 关键边界优先来自 `风险与未知数`
> - 如果前面跑过 `/grill-me`，不要漏掉其中已经识别出的风险场景

## 分阶段测试拆解

| 阶段 | 什么时候做 | 重点验证什么 | 通过后才能进入什么 |
|---|---|---|---|
| 阶段 1：前提验证 | 正式实现前 | 数据、脚本、配置、入口是否可用 | 最小主链路实现 |
| 阶段 2：最小主链路 | 第一轮实现后 | 主路径是否首次跑通 | 边界测试 |
| 阶段 3：关键边界 | 主路径通过后 | 高风险边界、异常样本、极端输入 | 阶段回归 |
| 阶段 4：阶段回归 | 每轮关键改动后 | 已通过项是否被打坏 | 扩量或下阶段计划 |
| 阶段 5：扩量前检查 | 准备扩大数据/运行时长/范围前 | 是否值得进入高成本测试 | 扩量测试 |
| 阶段 6：最终验收测试 | 收口前 | 完整指标、交付口径、最终证据 | 最终验收 |

> 推荐做法：
> - 每一阶段先在本页定义怎么测
> - 测完后再去 `test-report.md` 回写结果
> - 没有阶段测试报告，不建议直接推进到下一高成本阶段

## 每阶段测试报告最少应包含什么

- [ ] 测试方法
- [ ] 使用的数据 / 样本范围
- [ ] 实际执行命令或人工检查动作
- [ ] 关键指标或现象摘要
- [ ] 真实截图 / 对比图 / 可视化证据
- [ ] LLM 或独立审查给出的阶段裁决

> 不建议只写“测试通过”四个字。
>
> 更推荐每阶段都留下：
> - 方法是怎么测的
> - 数据是拿什么测的
> - 看到了什么真实结果
> - 下一步到底是继续、小调、大改，还是回到需求/方案层

## 备注

- `test-plan.md` 负责定义“怎么验证它通过”
- `test-report.md` 负责记录“每个阶段到底测得怎么样，能不能继续推进”
- 推荐让 `test-report.md` 明确输出阶段裁决：
  - `通过`
  - `微调`
  - `大改`
  - `调整需求`
  - `调整方案`
- 如果前面已有 `task.md` 或 `/grill-me` 输出，优先继承其中的目标、风险、日志策略
- 如果任务属于 debug / 回归 / 偶发问题，不要跳过“日志采集”一节
- 如果任务链路很长，优先把大测试拆成多轮阶段测试，不要把风险全压到最终测试
- 如果任务属于硬件 / 嵌入式，再补下面几项：
  - [ ] 原理图 / 引脚映射已人工核对
  - [ ] 外设时钟 / 中断 / 工程树纳管已人工核对
  - [ ] 串口或其他观测路径已验证可用
  - [ ] 最小落板证据已定义
