# 软件开发画像

> 适合功能开发、Bug 修复、接口改造、脚本工具和工程治理类任务。

## 推荐公开模板

| 场景 | 默认入口 | 何时升级 |
|---|---|---|
| 小修复、单文件脚本 | `task-lite.md` | 验证超过 10 分钟或开始跨模块时升级 |
| 常规功能开发 | `task.md` | 涉及多个子任务或阶段 Gate 时升级 |
| 跨模块改造 | `task-full.md` | 需要更细拆分和隔离边界 |

核心控制面默认保留：`requirements-checklist.md`、`steps.md`、`acceptance.md`、`test-plan.md`、`test-report.md`。

## 测试与证据重点

- 单元测试：最小行为是否正确
- 集成测试：模块协作是否正常
- 回归测试：旧路径是否被打坏
- 兼容检查：接口、配置、脚本入口是否保持可用

常见证据包括命令输出、日志片段、接口返回结果、关键 diff 说明。

## 常拉起的内部件

| 内部件 | 触发条件 |
|---|---|
| `requirements-source.md` | 需求来自 issue、邮件、聊天、PRD 的混合输入 |
| `source-requirements-alignment.md` | 涉及多个验收点，担心需求漏记 |
| `change-request.md` | 中途新增范围、接口约束或回归风险 |

## `/grill-me` 应追问什么

- 哪个模块是主改动面
- 哪些接口不能破坏
- 哪些回归路径必须补测
- 是否允许顺手重构

如果这些边界都很清楚，就直接生成任务卡，不要过度访谈。
