# Txxx — 分阶段测试报告

> 这不是最终一次性总报告，而是执行链路中的阶段性测试证据。目标是尽早发现方向错误、数据错误、方法错误，避免等几小时后才在最终测试里爆雷。

## 使用原则

- 每进入一个高成本阶段前，先做一轮当前阶段最小必要测试
- 每做完一轮关键实现后，先写这一页，再决定是否继续推进
- 测试报告优先短、小、可比对，不追求一次写成大而全总结
- 推荐先由执行者回填事实，再由独立审查者或人工做“测试审查”
- 推荐正文直接嵌入关键真实截图，让 LLM 和人工都能少跳转地看证据

- `通过`

- `大改`
- `调整需求`
- `调整方案`

对应理解：

- `通过`：当前阶段证据充分，可推进
- `微调`：方向基本对，小范围修正后重测
- `大改`：实现或方法明显不稳，不建议直接继续扩量
- `调整需求`：测试暴露出原需求理解或边界定义有问题，应回到需求层
- `调整方案`：需求没变，但当前方案路线、方法或数据口径需要重定

## 回写约定

- `test-plan.md` 负责定义“怎么测”
- `test-report.md` 负责记录“测了什么、结果如何、能不能继续”
- 推荐让 LLM 或独立审查者基于：
  - 测试方法
  - 数据说明
  - 关键指标
  - 真实截图
  做一次阶段裁决，而不是只看一句“测试通过”
- `/gate` 在执行前、阶段切换前，优先先看这份报告
- 若本轮测试表明方向不对，不要只改代码；先更新方案、计划、需求表，再重新审查
