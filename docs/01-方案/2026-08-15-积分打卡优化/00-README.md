## 一句话结论

当前系统已能闭环「学习 → 得阳光 → 花阳光（喂伙伴/兑奖励）→ 徽章」，**不需要推倒重来**。要做的是四类事：

1. **口径统一（P0）**：打卡定义在文档与代码间自相矛盾（"全日完成" vs "首次得阳光"），裁决为**双层口径**——"点亮日"（首次有效行动，自动沉淀）+ "完美日"（全日任务完成，供徽章用），并把"打卡"文案改为"点亮"，呼应《什么是真正的工作台》"不人为打卡、由真实动作自动沉淀"的主张。
2. **账本补漏（P0）**：向日葵等旁路加阳光不进 `totalSunlightEarned`，导致徽章/成长统计口径漂移；修复为全部走同一记账约定。
3. **可见性与"还差一点"（P1）**：借鉴 Kids-Reward-Chart（MIT）与 StarKids 的"还差 X"进度提示；把日历升级为 GitHub 式行动热力图；两套徽章（19 枚成就 + 11 枚世界里程碑）统一到一个收集箱展示层。
4. **明确不做**：不加第二货币、不做排行、不做惩罚、不恢复"券"（2026-08-14 已否决）、不给学习路径加每日总分上限、不动 `workbench-bridge.js` 的日上限 80 与单事件上限 40。

## 不可违反的前置决策（继承）

1. 阳光是唯一账本（D 系列决策 + `docs/02-课程/幼儿课程方案/06-成长与游戏/积分阳光计划.md`）。
2. 奖励幂等：同 eventId 只发一次；错误/失败不扣分、无任何惩罚机制。
3. 券已否决（2026-08-14），用阳光日上限 80 + eventKey 去重替代。
4. 星芒是唯一伙伴主角，不引入外部 IP。
5. 不做公开排行 / 人与人对比 / 复杂积分经济。
